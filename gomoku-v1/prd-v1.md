# Gomoku Lite PRD（20×20 / 双场景复古 BGM / 非 AI 人机策略版）

## 1. 项目目标

开发一个基于 Web 的完整五子棋小游戏项目，项目名称为 `Gomoku Lite`。

该项目必须：

* 运行在现代浏览器中
* 同时兼容桌面端和移动端竖屏
* 采用 `React + Vite + Canvas API` 实现
* 交付为完整可运行工程，而不是代码片段
* 所有源码文件和文档统一采用 `UTF-8` 编码
* 所有界面文案统一使用简体中文，不允许乱码

该项目面向“即开即玩”的轻量小游戏场景，强调：

* 规则明确
* UI 简洁但完整
* 20×20 棋盘可稳定运行
* 人机对战逻辑可感知地分级
* 背景音乐具有明确的复古电子游戏氛围
* 模块结构清晰，便于未来扩展

## 2. 交付形式与强制约束

Codex 在生成项目时必须遵守以下硬性要求：

* 必须生成完整项目目录
* 必须生成 `package.json`
* 必须生成 `vite.config.js`
* 必须生成 `index.html`
* 必须生成 `src/` 目录
* 必须包含可直接运行的 React 项目
* 不允许只输出单个 HTML 文件
* 不允许把所有逻辑写进一个文件
* 必须按模块拆分代码
* 最终必须能执行：

  * `npm install`
  * `npm run dev`
  * `npm run build`
* `npm run build` 必须成功

额外强制约束：

* 不需要后端
* 不需要数据库
* 不依赖任何服务端 API
* 不允许接入任何机器学习模型、LLM、云端推理服务或外部棋力引擎
* 人机对战必须完全基于本地规则、权重、模式识别和确定性逻辑实现
* 若真实音频文件无法提供，必须使用 Web Audio API 生成可运行的替代实现，不能留空
* 音频必须考虑浏览器自动播放限制，需在用户首次交互后再启动 `AudioContext`

## 5. 核心模块职责

### 5.1 GameManager

负责：

* 游戏状态流转
* 当前玩家切换
* 游戏模式管理
* 难度管理
* 胜负判定调用
* 机器回合调度
* 对局开始、结束时切换对应背景音乐

### 5.2 Board

负责：

* 初始化 20×20 棋盘
* 管理落子
* 查询棋盘格子状态
* 存储落子历史
* 提供合法落点判断

### 5.3 Rule

负责：

* 胜利判定
* 平局判定
* 连五方向检测
* 返回获胜连线坐标，供 Canvas 高亮绘制

### 5.4 CandidateGenerator

负责：

* 基于当前已落子区域筛选候选空位
* 默认只考虑距离已有棋子一定范围内的空位
* 控制 20×20 棋盘下的人机计算成本

### 5.5 PatternEvaluator

负责：

* 在横向、纵向、两条斜线四个方向上评估棋型
* 分别计算进攻分与防守分
* 识别成五、活四、冲四、活三、眠三、活二等关键模式
* 为不同难度提供差异化评分依据

### 5.6 MachinePlayer

负责：

* 根据难度输出机器落子位置
* 使用纯本地确定性规则实现三档难度
* 不允许调用任何外部 AI 能力
* 支持“立即获胜”“立即防守”“布局成长”“阻断威胁”等优先级逻辑

### 5.7 AudioManager

负责：

* 菜单 BGM
* 对局 BGM
* 按钮音效
* 落子音效
* 胜利音效
* 声音总开关
* BGM 与音效分别开关或统一开关的管理
* 首次用户交互后激活音频上下文

## 6. 游戏规则

### 棋盘

* 棋盘大小：`20 × 20`
* 总格数：`400`

### 棋子定义

* `0` = 空
* `1` = 黑子
* `2` = 白子

### 基础规则

* 黑子先手
* 双方轮流落子
* 不允许落在已有棋子的位置
* 横向、纵向、左斜、右斜任意连续 5 子即为获胜
* 不启用禁手规则
* 不检测三三禁手
* 不检测四四禁手
* 不检测长连禁手
* 棋盘落满且无人形成五连则为平局

### 棋盘数据结构

```js
board[20][20]
```

### 落子历史

```js
moveHistory = [
  { x, y, player, timestamp }
]
```

说明：

* `moveHistory` 用于对局记录与未来扩展
* 本次版本不强制实现悔棋，但结构必须为未来加入悔棋预留空间

## 7. 游戏模式

项目必须支持两种模式：

### 7.1 玩家对玩家（PVP）

规则：

* 玩家 1 使用黑子
* 玩家 2 使用白子
* 两人在同一设备轮流下棋

### 7.2 玩家对机器（PVE）

规则：

* 玩家使用黑子
* 机器使用白子
* 玩家先手
* 机器下棋前需要有 `250ms - 500ms` 的思考延迟
* 延迟可使用 `setTimeout`
* 机器落子期间必须暂时锁定玩家输入，避免重复点击

## 8. 人机策略总原则

本项目的人机逻辑必须参考“候选区域筛选 + 单点权重计算 + 优先级决策”的本地规则思路实现：先缩小可下区域，再对每个候选点在四个方向上计算权重，并对“成五、成四、阻断威胁”等场景设定明确优先级；不允许接入任何外部 AI。该参考来源的 README 明确描述了“先计算可选择区域，再为格子计算权重，并按成五、成四、阻止对方等优先级选择最佳点”的实现思路。([GitHub][1])

强制要求如下：

* 不允许全盘随机下棋充数
* 不允许仅靠简单随机在三档难度间伪造差异
* 三档难度必须在“是否防守、是否布局、优先级覆盖范围、评分维度”上有真实差异
* 所有难度都必须优先处理“自己当前一步可直接获胜”的情况
* 中高难度必须处理“对手下一步可直接获胜”的情况
* 候选落点应优先限制在距离已有棋子 `1~2` 格范围内的空位
* 若棋盘为空，首步落点应在棋盘中央附近区域，而不是角落
* 评分时至少考虑四个方向：

  * 横向
  * 纵向
  * 左上到右下
  * 右上到左下

## 9. 三档人机难度规则

这是本项目最重要的部分之一。难度必须在主菜单中可选，并且行为差异必须符合以下定义。

### 9.1 新手模式

目标：

* 让玩家容易获胜
* 机器表现出基础连线意识，但防守较差

实现规则：

* 机器先检查自己是否可以一步成五；若可以，立即获胜
* 若不能直接获胜，则主要依据“自身进攻分”选择落点
* 对玩家威胁只做极弱感知
* 不强制拦截玩家的活三、冲四或潜在杀棋
* 可加入少量随机扰动，但必须建立在候选点评分之上，不能纯随机

评分倾向：

* 进攻分权重高
* 防守分权重低
* 更像“只顾自己连线成长”

验收感受：

* 玩家应明显感受到新手模式经常漏防
* 玩家通过简单进攻即可击败机器

### 9.2 普通模式

目标：

* 机器具备基本对抗能力
* 既会进攻也会处理最明显的防守需求

实现规则：

* 机器先检查自己是否可以一步成五；若可以，立即获胜
* 若玩家下一步可以成五，必须优先堵住
* 在无立即胜负点时，同时计算进攻分和防守分
* 能识别并处理以下主要威胁：

  * 对手冲四
  * 对手活三
  * 对手多方向延展趋势
* 倾向于选择“既能发展自己，又能限制对方”的位置
* 不需要复杂搜索，但必须具备稳定的一步前瞻逻辑

评分倾向：

* 进攻分与防守分接近均衡
* 对“阻断对方直接威胁”的优先级高于普通布局

验收感受：

* 玩家会觉得机器“开始会堵了”
* 普通玩家不能轻松碾压，但仍有明显取胜机会

### 9.3 专家模式

目标：

* 在不引入 AI 的前提下，尽可能做出强而稳定的规则型对手

实现规则：

* 机器先检查自己是否可以一步成五；若可以，立即获胜
* 若玩家下一步可以成五，必须立即堵住
* 若出现多个紧急点，必须依据优先级表精确处理
* 必须识别并优先处理以下关键棋型：

  * 成五
  * 双向成五机会
  * 活四
  * 冲四
  * 双活三
  * 强延展活二 / 活三
* 在无立即胜负点时，必须综合考虑：

  * 自己能否形成强进攻
  * 对方是否正在形成复合威胁
  * 一个点是否同时具备“进攻 + 防守”双价值
* 允许使用“局部两步规则推演”增强棋力，但必须是确定性逻辑，不得引入通用博弈 AI 框架
* 专家模式必须明显强于普通模式，不得只是分数系数略微增加

评分倾向：

* 明确的优先级表 + 多维评分叠加
* 对双威胁、复合威胁、连续做势有更高敏感度

验收感受：

* 玩家能明显感受到专家模式会主动做局
* 专家模式不只是会堵，更会创造自己的胜势

## 10. 人机优先级体系要求

为了让另一个 Codex 更稳定地生成可玩的机器逻辑，必须实现清晰的优先级体系。

建议优先级从高到低如下：

1. 自己当前一步可成五，立即落子获胜
2. 对手下一步可成五，立即堵住
3. 自己可形成活四或双重高危胜势
4. 对手可形成活四或双重高危胜势，立即处理
5. 自己可形成冲四并兼顾其他线路成长
6. 落点同时具备“防守 + 进攻”双收益
7. 形成活三、双活二等持续布局
8. 普通延展点
9. 候选点分数相同时，优先靠近当前棋群中心
10. 仍相同时，可按稳定顺序取点，避免每局表现完全飘忽

说明：

* 上述优先级必须编码进逻辑中
* 不允许只给一个总分而完全没有紧急情况兜底规则
* 高难度必须先走优先级判定，再比较权重

## 11. 游戏状态机

游戏必须包含以下状态：

* `MENU`
* `PLAYING`
* `GAME_OVER`

状态流转：

```text
MENU
→ 选择 PVP 或 PVE
→ 若为 PVE 则选择难度
→ PLAYING
→ 胜利 / 平局
→ GAME_OVER
→ 再来一局 / 返回菜单
```

必须由 `GameManager` 统一控制状态切换。

## 14. 音频要求

### 14.1 背景音乐总要求

本项目必须具备背景音乐，且必须区分两个场景：

* 菜单栏 BGM
* 对弈期间 BGM

共同要求：

* 风格必须明显接近 80 年代电子游戏的复古电子音乐
* 必须有旋律感，不能只是噪声、蜂鸣或无组织音序
* 允许通过 Web Audio API 合成，无需真实 mp3 / wav 文件
* 允许使用方波、三角波、脉冲波、简易鼓点来模拟 8-bit / chiptune 质感
* 必须支持循环播放
* 必须支持静音 / 关闭
* 用户关闭声音后，不应播放任何 BGM 或音效

### 14.2 菜单栏 BGM

风格要求：

* 氛围偏轻松、欢迎、复古
* 节奏相对舒缓
* 有明确主旋律和简短循环段
* 不应太紧张或压迫

建议特征：

* `90 ~ 110 BPM`
* 使用较轻的节奏和分解和弦
* 可偏向“标题画面 / 主菜单”感

### 14.3 对弈期间 BGM

风格要求：

* 氛围偏紧张、专注、对抗
* 节奏感强于菜单 BGM
* 与菜单 BGM 明显不同，不能只是同一旋律换音色

建议特征：

* `120 ~ 145 BPM`
* 有更强的低频节奏支撑
* 更适合“下棋思考 / 对抗中”场景

### 14.4 BGM 切换规则

必须满足：

* 进入菜单时播放菜单 BGM
* 开始对局时切换到对局 BGM
* 返回菜单时切回菜单 BGM
* 切换时允许直接切歌，也允许做 `100ms - 400ms` 的淡入淡出
* 不允许两个 BGM 同时播放

### 14.5 必须保留的音效

* 按钮点击音效
* 落子音效
* 胜利音效

### 14.6 音效实现方式

* 允许使用 Web Audio API 直接生成简单音效
* 不强制提供 mp3 / wav 文件
* 音效风格应与整体复古电子游戏氛围一致

### 14.7 音量要求

* 落子音效必须明显可感知
* 落子音效音量应明显高于按钮点击音效
* 胜利音效应清晰但不要刺耳
* BGM 默认音量必须低于落子音效，避免影响操作反馈

### 14.8 声音控制

必须支持：

* 一键开启 / 关闭全部声音
* 至少记忆本次页面生命周期内的声音状态
* 可选实现：将声音设置持久化到 `localStorage`

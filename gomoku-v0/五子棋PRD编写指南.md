# 五子棋项目 PRD 编写指南

## 目的

这份文档用于总结当前五子棋小游戏项目从最初 `gomoku_prd.md` 到后续多轮补充需求之间暴露出来的问题，并反向整理出一份更适合直接交付给 Codex 的 PRD 编写规范。

目标是让你下次只用一份 PRD，就能更大概率一次性生成完整、可运行、少返工的项目。

---

## 一、这次项目里实际经历过的需求补充

初始 PRD 已经明确了以下内容：

- 项目类型：Web 五子棋小游戏
- 技术栈：React + Vite + Canvas
- 模块结构：`GameManager / Board / Rule / MachinePlayer / AudioManager`
- 玩法模式：`PVP / PVE`
- 基础规则：15x15、五子连珠、无禁手、平局判定
- UI 结构：菜单、棋盘、状态栏、结果弹窗
- 基础音效：背景音乐、落子音效、胜利音效、按钮音效
- 代码组织：模块化、组件拆分、逻辑与 UI 分离

但在真正实现后，后续又追加了这些关键要求：

### 1. 人机难度必须明确分级

后续补充要求指出：

- 需要 `新手 / 高手 / 专家` 三档难度
- 三档机器策略必须明显不同
- 不只是“更强一点”，而是行为规则要能被描述清楚

你后面最终明确的规则是：

- 新手：机器只知道自己连成 5 个子
- 高手：机器只知道堵玩家，不让玩家胜利
- 专家：机器既知道堵玩家，也会追求自己连成 5 个子

这说明：

如果 AI 难度是项目重点，PRD 里必须直接写成“行为规则”，不能只写“新手、高手、专家”这种模糊词。

### 2. 音效不能只写“有”

后续补充要求指出：

- 落子音效太小，需要放大至少 10 倍
- 背景音效不能只是存在，而要符合预期
- 后面你又明确要求直接删除背景音乐

这说明：

如果音频体验有偏好，PRD 需要写清楚：

- 是否真的要背景音乐
- 背景音乐的风格是什么
- 是否允许程序生成音频代替真实音频文件
- 各类音效之间的相对音量关系
- 是否需要静音开关

否则很容易出现“功能有了，但体验不对”的返工。

### 3. 编码和文本质量也应属于 PRD 范围

后续补充要求指出：

- 需要修复中文乱码
- 要求统一 UTF-8

这说明：

如果项目里包含中文界面文案，PRD 应该显式写明：

- 所有源码文件统一使用 UTF-8
- 所有界面文案为简体中文
- 不允许乱码或本地编码混用

### 4. “专家模式永远不会输”这类描述不适合直接写成绝对承诺

你曾要求：

- 专家模式“永远不会输给玩家”

后来又把规则重新收敛成：

- 专家模式同时会堵玩家并追求自己连成五子

这说明：

在纯前端小游戏里，如果不引入真正完备的博弈搜索、缓存、剪枝深度设计和严格证明，像“永远不会输”这种绝对承诺通常不适合写进 PRD。

更适合写成：

- 专家模式优先保证不漏防致命威胁
- 专家模式优先处理立即获胜与立即防守
- 专家模式在候选点中综合进攻与防守评分

这样更可实现，也更便于验收。

---

## 二、为什么最初 PRD 没能一次性交付到你最终想要的状态

根本原因不是“PRD 不够长”，而是“有些决定性约束没有写死”。

这次返工主要集中在 4 类地方：

### 1. 功能边界写了，但行为边界没写

例子：

- 写了有 PVE
- 但没有写 AI 难度如何定义
- 写了有背景音乐
- 但没有写背景音乐风格、是否可接受程序生成音频

这会导致首次实现只能按“合理猜测”落地，而不是按“唯一标准”落地。

### 2. 有模块清单，但没有验收标准

例子：

- 写了 `MachinePlayer`
- 但没有写清楚：怎么判定“新手”和“高手”真的不一样

因此首次实现虽然模块存在，但未必符合你对玩法的真实期待。

### 3. 有 UI 结构，但没有说明文案和交互质量要求

例子：

- 有菜单、状态栏、弹窗
- 但没规定：菜单是否支持难度二级选择、状态栏是否显示难度、文案必须是中文且无乱码

### 4. 有音频需求，但没有指定实现方式与可接受下限

例子：

- PRD 里要求有 `bgm.mp3 / place.wav / win.wav / click.wav`
- 但当前项目实际使用的是 Web Audio 合成音

这并不是实现错误，而是 PRD 没有明确：

- 必须提供真实音频文件
- 还是允许程序生成音效替代

## 三、下次给 Codex 的 PRD 应该至少包含哪些内容

下面这套结构，适合用于“直接生成完整小游戏项目”。

---

## 1. 项目目标

这一段要回答：

- 这是个什么游戏
- 跑在哪
- 给谁玩
- 核心体验是什么

建议写法：

```md
开发一个基于 Web 的五子棋小游戏，运行在移动端和桌面浏览器中。

核心体验：
- 打开即玩
- 菜单清晰
- 棋盘操作流畅
- 人机模式具备清晰可感知的三档难度差异
- 界面文案全部为简体中文
- 所有源码文件统一使用 UTF-8 编码
```

---

## 2. 技术栈与工程约束

这一段要明确：

- 必须使用什么技术
- 目录结构是否强制
- 是否必须生成完整工程

建议写法：

```md
技术栈要求：
- React + Vite
- 使用函数组件与 Hooks
- 棋盘绘制使用 Canvas API
- 不需要后端
- 不依赖数据库

工程要求：
- 必须生成完整可运行项目
- 必须包含 package.json
- 必须可通过 npm install 和 npm run dev 启动
- 必须可通过 npm run build 构建成功
- 所有源码采用 UTF-8 编码
```

---

## 3. 功能清单

这一段不能只列模块名，必须列玩家能感知到的功能。

建议写法：

```md
必须实现以下功能：
- 主菜单
- 玩家对玩家模式
- 玩家对机器模式
- 人机难度选择：新手 / 高手 / 专家
- 棋盘落子
- 当前回合提示
- 重新开始
- 返回菜单
- 游戏结束弹窗
- 胜负判定
- 平局判定
- 静音开关
```

---

## 4. 游戏规则

这一段你原始 PRD 已经写得比较完整，但建议加上“不可省略”的验收措辞。

建议写法：

```md
棋盘：15x15
黑子先手
双方轮流落子
任意方向连续 5 子即获胜
不启用禁手规则
棋盘满且无人五连则为平局
不允许覆盖已有棋子
```

---

## 5. AI 规则必须写成“行为定义”

这是本次最重要的经验。

如果你希望一次性做对，必须像下面这样写：

```md
PVE 模式下提供三档难度：

1. 新手
- 机器只考虑自己的连线成长
- 如果自己当前一步可以直接形成五连，则立即获胜
- 否则只选择更有利于自己连线的位置
- 不主动防守玩家

2. 高手
- 机器只考虑防守玩家
- 如果玩家下一步有机会形成五连，则优先堵住
- 否则优先落在更能破坏玩家连线的位置
- 不主动追求自己的连线胜利

3. 专家
- 如果机器当前一步可以形成五连，则立即获胜
- 如果玩家下一步有机会形成五连，则立即堵住
- 否则综合考虑进攻与防守，优先选择既能扩大自己连线、又能限制玩家的位置
```

如果你想要更强 AI，也要写得更明确：

```md
专家模式验收要求：
- 必须优先处理“立即获胜”和“立即防守”
- 候选点必须只从已有棋子附近选取
- 需要对候选点进行进攻评分和防守评分
- 不要求证明永远不输，但要显著强于高手模式
```

这里的关键原则是：

不要写“更聪明”“更强”“像高手一样下棋”这种抽象描述，要写它到底“看到什么”和“优先做什么”。

---

## 6. 音频需求要具体写清

本次返工最多的地方之一就是音频预期不明确。

建议写法：

```md
音频要求：
- 保留落子音效
- 保留按钮点击音效
- 保留胜利提示音效
- 不需要背景音乐
- 所有音效允许使用 Web Audio API 程序生成，不强制提供真实 mp3 / wav 文件
- 落子音效应明显可感知，音量高于按钮点击音效
- 提供声音开关按钮
```

如果你确实要背景音乐，应该这样写：

```md
背景音乐要求：
- 需要轻量背景音乐
- 风格：古风、轻柔、循环不刺耳
- 音量约为落子音效的 30%
- 若无法提供真实音频文件，可使用 Web Audio API 生成简单旋律替代
```

否则模型只能猜。

---

## 7. UI 要求也要写验收项

建议写法：

```md
UI 要求：
- 菜单、棋盘、状态栏、结果弹窗必须拆分为独立组件
- 菜单中必须能直接选择 PVP，或选择 PVE 后进一步选择难度
- 状态栏必须显示：当前模式、当前回合、PVE 当前难度
- 所有按钮文案必须为简体中文
- 所有界面文案不得出现乱码
- 界面适配移动端竖屏，同时兼容桌面浏览器
```

---

## 8. 编码与文本要求应单独成节

建议直接写：

```md
文本与编码要求：
- 所有源码文件统一保存为 UTF-8
- 所有界面文案使用简体中文
- 禁止出现乱码、英文占位文案或未翻译内容
```

这条非常值钱，因为它能直接避免一类低级返工。

---

## 9. 验证要求也要写

这会逼迫一次性交付时就自检，而不是只“写完代码”。

建议写法：

```md
交付要求：
- 生成完整可运行项目
- 运行 npm install 无报错
- 运行 npm run build 无报错
- 所有核心玩法可在浏览器中完成
- 不允许只输出代码片段
- 不允许省略 package.json 或 vite 配置
```

## 四、最适合直接交给 Codex 的 PRD 模板

下面是一份更适合一次性生成项目的写法模板。

```md
# 五子棋小游戏 PRD

## 1. 项目目标
开发一个基于 Web 的五子棋小游戏，运行在移动端和桌面浏览器中。
要求打开即玩，界面为简体中文，源码统一采用 UTF-8 编码。

## 2. 技术栈
- React
- Vite
- Canvas API
- JavaScript 或 TypeScript 均可
- 不需要后端
- 不需要数据库

## 3. 工程要求
- 必须生成完整可运行项目
- 必须包含 package.json / vite.config.js / index.html / src 目录
- 必须支持 npm install、npm run dev、npm run build
- 代码必须模块化，不能把所有逻辑写在一个文件里

## 4. 必须包含的核心模块
- GameManager
- Board
- Rule
- MachinePlayer
- AudioManager

## 5. 游戏规则
- 棋盘大小：15x15
- 黑子先手
- 双方轮流落子
- 横向、纵向、左斜、右斜任意连续 5 子即获胜
- 不启用禁手规则
- 棋盘满且无人五连为平局
- 不允许覆盖已有棋子

## 6. 游戏模式
### PVP
- 玩家 1 为黑子
- 玩家 2 为白子

### PVE
玩家为黑子，机器为白子。
提供三档难度：

1. 新手
- 机器只考虑自己的连线成长
- 若当前一步可直接五连则立即获胜
- 否则只选择更有利于自己连线的位置
- 不主动防守玩家

2. 高手
- 机器只考虑防守玩家
- 若玩家下一步可能五连则立即堵住
- 否则优先选择最能干扰玩家连线的位置
- 不主动追求自己的胜利

3. 专家
- 若机器当前一步可直接五连则立即获胜
- 若玩家下一步可能五连则立即堵住
- 否则同时考虑进攻与防守，优先选择兼顾自己连线与破坏玩家连线的位置

## 7. UI 组件
- Menu
- GameBoard
- StatusBar
- ResultModal

## 8. UI 要求
- 主菜单可选择 PVP 或 PVE
- 若选择 PVE，必须能选择新手 / 高手 / 专家难度
- 状态栏必须显示当前回合、当前模式、当前难度
- 游戏结束后弹窗显示黑子获胜、白子获胜或平局
- 提供重新开始和返回菜单按钮
- 界面适配移动端竖屏，同时兼容桌面浏览器

## 9. 音频要求
- 保留落子音效
- 保留按钮点击音效
- 保留胜利音效
- 不需要背景音乐
- 可使用 Web Audio API 程序生成音效，不强制提供真实音频文件
- 落子音效音量应明显高于按钮点击音效
- 提供声音开关

## 10. 编码与文案要求
- 所有源码文件统一为 UTF-8
- 所有界面文案必须为简体中文
- 不允许乱码

## 11. 交付要求
- 输出完整工程，不是代码片段
- 项目必须可以直接运行
- npm run build 必须成功
- 所有模块拆分清晰
```

## 五、如果你想让 Codex 一次成功，输入 PRD 时最重要的 6 条原则

### 原则 1：不要只写“有什么”，要写“怎么判定做对了”

比如不要只写：

- 有人机模式

而要写：

- 人机模式分三档，每档决策规则分别是什么

### 原则 2：AI 需求必须写成优先级规则

例如：

- 若机器当前一步可赢，立即赢
- 若玩家下一步可赢，立即堵
- 否则再比较进攻与防守评分

### 原则 3：音频需求必须写是否允许程序生成

否则容易出现你想要真实音乐，但实际实现成 Web Audio 合成音的情况。

### 原则 4：中文项目必须显式声明 UTF-8

否则在某些环境下就容易出现乱码。

### 原则 5：把“必须完成构建验证”写进 PRD

否则容易出现“代码写完了但没验证”的情况。

### 原则 6：避免写不可验证的绝对描述

例如：

- 永远不会输
- 非常智能
- 很像真人

这类话不适合作为验收标准。

应该改成：

- 优先处理直接获胜和直接防守
- 采用候选点评分策略
- 专家模式强于高手模式

---

## 六、结论

如果你希望 Codex 尽量一次性成功完成项目，PRD 最关键的不是“写得多”，而是：

- 把功能写成可验收的规则
- 把 AI 写成明确的优先级行为
- 把音频、编码、文案这些容易被默认处理的细节显式写死
- 把“必须可运行、必须构建成功”写成硬约束

对这个五子棋项目而言，最关键的遗漏点其实只有三类：

- AI 行为规则没写死
- 音频预期没写死
- 中文编码要求没写死

只要这三类在 PRD 里提前写清，项目一次性交付成功率会明显提高。
